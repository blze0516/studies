## 1. Acceptance Criteria와 Definition of Done의 역할

### Acceptance Criteria

개별 요구사항이 **어떤 조건에서 만족되었다고 볼 수 있는지**를 검증 가능한 문장으로 정의한다.

```text
Requirement
→ Acceptance Criteria
→ 구현
→ 검증 Evidence
```

### Definition of Done

개별 기능 하나가 아니라 **이번 제출을 완료했다고 말하기 위한 공통 완료 조건**을 정의한다.

```text
기능 동작만 함
≠
제출 완료

기능 + 검증 + 실행 방법 + 범위 확인
=
Done 후보
```

## 2. Given / When / Then 작성 규칙

```text
Given = 시작 조건 / 이미 주어진 상태
When  = 사용자가 하거나 시스템에 발생시키는 행동
Then  = 밖에서 확인 가능한 결과
```

좋은 기준은 다음 특성을 가진다.

- 한 번 읽었을 때 성공/실패를 판단할 수 있다.
- `적절히`, `잘`, `빠르게`, `정상적으로` 같은 애매한 단어에 의존하지 않는다.
- 구현 방법보다 **관찰 가능한 behavior**를 적는다.
- 원문에 없는 정책을 사실처럼 추가하지 않는다.
- 필요한 가정은 별도로 표시한다.

## 3. 오늘의 Working Assumption

Day 2의 Q-02는 아직 실제 출제자의 답을 받지 못했다. 따라서 학습을 진행하기 위해 다음을 **원문 사실이 아닌 실습용 가정**으로 사용한다.

> **WA-01**: 프로젝트가 문서화한 기준 시각에서 `slotStart <= now`이면 과거/현재 슬롯으로 보고 새 예약을 허용하지 않는다.

실제 과제에서 출제자가 다른 정책을 주면 이 가정과 관련 Acceptance Criteria를 즉시 수정한다.

영업시간과 timezone의 구체적인 값은 아직 고정하지 않는다. 아래 기준에서는 **“프로젝트에 문서화된 예약 가능 시간 범위”**, **“프로젝트에 문서화된 기준 timezone”**이라는 표현을 사용한다.

# 4. Core Acceptance Criteria — 정확히 15개

## AC-01 — 예약 가능한 날짜의 슬롯 조회

**Given** 프로젝트의 예약 가능 시간 범위 안에 아직 예약되지 않은 미래 슬롯이 존재하고  
**When** 사용자가 해당 날짜의 예약 가능한 시간을 조회하면  
**Then** 예약 가능한 슬롯 목록을 확인할 수 있다.

- 연결: `FR-01`
- Evidence 후보: 대표 조회 예시 / 이후 API Test

---

## AC-02 — 슬롯은 30분 단위

**Given** 특정 날짜에 예약 가능한 시간이 존재하고  
**When** 사용자가 예약 가능한 슬롯을 조회하면  
**Then** 반환되는 각 슬롯의 시작과 종료 간격은 30분이다.

- 연결: `FR-01`, `CON-01`

---

## AC-03 — 이미 예약된 슬롯은 가용 목록에서 제외

**Given** 특정 날짜의 한 슬롯에 유효한 예약이 이미 존재하고  
**When** 사용자가 그 날짜의 예약 가능한 시간을 조회하면  
**Then** 이미 예약된 슬롯은 예약 가능 목록에 포함되지 않는다.

- 연결: `FR-01`, `FR-03`

---

## AC-04 — 지난 슬롯은 가용 목록에서 제외

**Given** 프로젝트의 시간 정책상 이미 지난 슬롯이 존재하고  
**When** 사용자가 예약 가능한 시간을 조회하면  
**Then** 그 지난 슬롯은 예약 가능 목록에 포함되지 않는다.

- 연결: `FR-01`, `FR-04`, `WA-01`

---

## AC-05 — 유효한 예약 생성

**Given** 미래의 예약 가능한 슬롯이 있고 유효한 이름과 이메일이 준비되어 있으며  
**When** 사용자가 해당 슬롯을 예약하면  
**Then** 예약이 생성되고 어떤 슬롯을 누가 예약했는지 확인할 수 있다.

- 연결: `FR-02`, `CON-04`

---

## AC-06 — 예약 생성 후 해당 슬롯은 더 이상 가용하지 않음

**Given** 예약 가능한 슬롯 하나가 있고  
**When** 사용자가 그 슬롯의 예약 생성에 성공한 뒤 다시 예약 가능한 시간을 조회하면  
**Then** 방금 예약한 슬롯은 예약 가능 목록에 포함되지 않는다.

- 연결: `FR-01`, `FR-02`, `FR-03`

---

## AC-07 — 빈 이름 거절

**Given** 예약 가능한 미래 슬롯이 있고 이름이 공백만 포함하거나 trim 후 비어 있으며  
**When** 사용자가 예약을 시도하면  
**Then** 예약은 생성되지 않고 입력 오류임을 확인할 수 있다.

- 연결: `FR-05`, `ASM-05`

---

## AC-08 — 이메일 누락 거절

**Given** 예약 가능한 미래 슬롯이 있고 이메일 값이 제공되지 않았으며  
**When** 사용자가 예약을 시도하면  
**Then** 예약은 생성되지 않고 입력 오류임을 확인할 수 있다.

- 연결: `FR-05`, `CON-04`

---

## AC-09 — 이메일 형식 오류 거절

**Given** 예약 가능한 미래 슬롯이 있고 이메일 형식으로 볼 수 없는 값이 제공되었으며  
**When** 사용자가 예약을 시도하면  
**Then** 예약은 생성되지 않고 입력 오류임을 확인할 수 있다.

- 연결: `FR-05`, `ASM-06`

---

## AC-10 — 이미 예약된 슬롯에 두 번째 예약 거절

**Given** 한 슬롯에 예약이 이미 존재하고  
**When** 다른 사용자가 같은 슬롯을 다시 예약하려고 하면  
**Then** 두 번째 예약은 성공하지 않는다.

- 연결: `FR-03`, `CON-03`

---

## AC-11 — 중복 시 기존 예약 보존

**Given** 한 슬롯의 첫 번째 예약이 이미 성공했고  
**When** 같은 슬롯에 대한 두 번째 예약 시도가 거절되면  
**Then** 기존 첫 번째 예약은 그대로 유지되고 추가 유효 예약은 생기지 않는다.

- 연결: `FR-03`, `CON-03`

---

## AC-12 — 과거 슬롯 예약 거절

**Given** 프로젝트 시간 정책상 과거인 슬롯이 있고  
**When** 사용자가 그 슬롯을 예약하려고 하면  
**Then** 예약은 생성되지 않는다.

- 연결: `FR-04`, `CON-02`

---

## AC-13 — 현재 시각 경계값 거절

**Given** 슬롯 시작 시각이 프로젝트 기준 `now`와 같고  
**When** 사용자가 그 슬롯을 예약하려고 하면  
**Then** `WA-01`에 따라 예약은 생성되지 않는다.

- 연결: `FR-04`, `WA-01`
- 주의: 실제 출제자 정책이 다르면 수정 대상

---

## AC-14 — 실패 요청은 예약 데이터를 만들지 않음

**Given** 잘못된 입력, 중복 슬롯 또는 과거 슬롯 중 하나의 실패 조건이 있고  
**When** 예약 요청이 실패하면  
**Then** 실패한 요청 때문에 새로운 유효 예약이 생기지 않는다.

- 연결: `FR-03`, `FR-04`, `FR-05`

---

## AC-15 — README에서 실행과 검증 경로 확인 가능

**Given** 평가자가 프로젝트를 처음 확인하고  
**When** README를 읽으면  
**Then** 프로젝트를 어떻게 준비하고 실행하며 핵심 검증을 어떻게 수행하는지 찾을 수 있다.

- 연결: `NFR-01`
- 구체적인 clean-clone 검증은 Day 6/47에서 강화

# 5. Optional Acceptance Criteria — Core 15개와 분리

예약 취소는 `TIMEBOX_PLAN.md`에서 **Could**이다. Core가 끝나기 전에 이 기준 때문에 제출을 지연시키지 않는다.

### OPT-AC-01 — 예약 취소

**Given** 취소 가능한 기존 예약이 있고 Core Complete Gate를 이미 통과했으며  
**When** 사용자가 예약 취소 기능을 구현하기로 선택해 해당 예약을 취소하면  
**Then** 그 예약은 더 이상 유효한 예약으로 취급되지 않는다.

> 실제 구현을 선택하지 않았다면 이 Optional criterion은 미충족이 아니라 **Out of current scope**로 기록한다.

# 6. 나쁜 Acceptance Criteria를 좋은 기준으로 바꾸기

| 나쁜 표현 | 문제 | 개선 방향 |
|---|---|---|
| 예약이 잘 된다 | `잘`의 기준이 없음 | 성공 조건과 결과를 명시 |
| 적절한 오류를 준다 | `적절한`이 검증 불가 | 어떤 실패가 성공하지 않아야 하는지 명시 |
| 빠르게 조회된다 | 측정 기준 없음 | 성능 요구가 있으면 수치/측정 방법 필요 |
| DB에 잘 저장된다 | 구현 방법 중심 | 사용자가 확인 가능한 예약 결과 중심 |
| 예외를 처리한다 | 어떤 예외인지 불명확 | 실패 조건별 observable outcome 분리 |

# 7. Definition of Done — Day 4 Baseline

아래는 **이번 학습용 예약 과제를 제출 가능한 상태라고 부르기 위한 공통 완료 기준**이다.

## Scope / Requirement

- [ ] `REQUIREMENTS.md`의 Must 범위가 현재 구현 범위와 일치한다.
- [ ] 미해결 Ambiguity는 질문 또는 Assumption으로 추적된다.
- [ ] Core Acceptance Criteria 15개 중 실제 구현 범위에 해당하는 기준을 설명할 수 있다.
- [ ] Optional을 Core보다 먼저 시작하지 않았다.

## Behavior

- [ ] 예약 가능 슬롯 조회 핵심 흐름을 확인했다.
- [ ] 유효 예약 생성 핵심 흐름을 확인했다.
- [ ] 중복 예약 금지 핵심 흐름을 확인했다.
- [ ] 과거/현재 경계 정책을 문서화하고 그 정책과 동작이 일치한다.
- [ ] 잘못된 입력이 성공 처리되지 않는다.

## Evidence

- [ ] 핵심 성공/실패 규칙에 검증 Evidence가 있다.
- [ ] 실제 실행한 명령과 관찰 결과를 구분해 기록한다.
- [ ] 구현하지 않은 항목을 구현했다고 표시하지 않는다.

## Delivery

- [ ] README에 준비/실행/검증 경로가 있다.
- [ ] 제출 전 불필요 파일, debug 내용, secret 여부를 확인한다.
- [ ] Known Limitation과 Out of Scope를 숨기지 않는다.

> Day 4에서는 DoD의 **문서 구조와 판단 기준**을 만든다. 실제 build/test/clean clone/CI 등의 구체 Evidence는 이후 해당 Day에서 추가된다.

# 10. Change Rule

Requirement나 출제자의 답변이 바뀌면 Acceptance Criteria도 함께 바뀌어야 한다.

예:

```text
Q-02 답변:
"현재 시각과 같은 슬롯은 예약 가능"

그러면:
WA-01 수정
→ AC-04 재검토
→ AC-12 재검토
→ AC-13 수정
→ 이후 관련 테스트도 수정
```

Acceptance Criteria는 한 번 쓰고 고정된 장식 문서가 아니라 **요구사항과 구현 사이의 살아 있는 계약**이다.
